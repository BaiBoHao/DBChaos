# 业务韧性指标与全程报告

DBChaos 通过已有的 `--wait-stable <BenchmarkSQL 结果目录>` 自动完成基线、故障、恢复三个阶段的业务成功 TPS 采集，并在 `reportTest()` 中输出指标和分析。业务负载需要单独启动，并持续运行到恢复观测结束；Demo 脚本已启动业务并传入结果目录，无需再配置环境变量。

```bash
java -jar target/DBChaos-0.0.1.jar txn uncommitted_txn \
  -duration 30000 -table bmsql_stock -holders 1 -rows 10 \
  --wait-stable /path/to/benchmark/results
```

不提供业务结果源时，原有故障注入仍可运行，报告明确说明六项业务指标不可获取，不用注入器自身 SQL 执行数替代业务吞吐量。`monitor baseline` 独立命令仍只采集基线，不执行全程实验。

## 指标定义

TPS 按成功完成的业务事务计数，排除 `error` 非空且非 `0` 的记录，以及 `--baseline-exclude-ttype` 指定的类型（默认 `DELIVERY_BG`）。错误事务另计数。时间分桶使用事务完成时刻 `sessionStart + elapsed`。

| 指标 | 获取方式 |
| --- | --- |
| P0 | 注入前通过稳定判定的最近 N 个完整窗口的平均成功 TPS。 |
| t0 | SQL 前置条件检查通过后、正式注入开始时的实际墙钟时间；包括注入器建立测试表及准备负载的时间。未开始故障则为空。 |
| Pd | `[t0, 撤销时刻)` 内完整窗口的最低成功 TPS；存在未被业务结果时间戳覆盖的完整窗口时不确认最低值。 |
| td | 首个达到 Pd 的统计窗口结束时间；精度受窗口长度限制。 |
| tr | 撤销后首次满足恢复判据的连续 N 窗口组的结束时间；超时未满足则为空，不以超时点伪造恢复时间。 |
| Pr | 已恢复时取该稳定窗口组平均 TPS；超时未恢复时取观测期末最近最多 N 个完整且已覆盖窗口的平均值，并分别报告是否稳定。数据不足时为空。 |

额外记录撤销时刻 `fault_withdrawal_epoch_ms`，定义为注入器执行及其清理逻辑返回的时间。所有内置实际故障入口已标记正式注入起点；占位的 `test_case` 没有实际故障，不会产生假的 t0。新注入器应在参数校验后、第一项正式注入操作前调用 `markFaultStarted()`；使用 `runPreflight()` 的注入器由该方法在预检成功后标记。

控制台时间使用带 `Z` 的 UTC ISO 8601，JSON 时间为 Unix epoch 毫秒；CSV 同时给出相对 t0 的时间。td 和 tr 是窗口结束时间，不是毫秒级定位的瞬时性能极值。

## 性能分析

- 最大吞吐下降：`(P0 - Pd) / P0 × 100%`。
- 平均吞吐下降：`(P0 - 故障完整窗口平均 TPS) / P0 × 100%`。
- 恢复至基线比例：`Pr / P0 × 100%`。
- 已弥补吞吐损失：`(Pr - Pd) / (P0 - Pd) × 100%`；没有吞吐损失时分母不可用，报告 N/A。
- 撤销后恢复耗时：`tr - 撤销时刻`；没有确认恢复时不提供此耗时。

下降比例为负表示吞吐量高于基线；恢复比例允许超过 100%。故障期间持续成功事务和错误事务还用于报告业务错误率，避免 TPS 尚可但错误率升高时宣称隔离有效。

默认判据及可选覆盖方式：

| 参数 | 默认值 | 含义 |
| --- | --- | --- |
| `--baseline-window` | 10 秒 | 基线、故障、恢复使用相同的统计窗口。 |
| `--baseline-stable-windows` | 3 | 恢复判定需要连续 N 个完整窗口。 |
| `--baseline-tps-cv` | 5% | 连续恢复窗口的成功 TPS 变异系数上限。 |
| `--recovery-ratio` | 95% | 每个恢复窗口 TPS 均须达到该比例的 P0；仅稳定在低水平不算恢复。 |
| `--recovery-timeout` | 180 秒 | 撤销后最长观测时间；判定恢复后可提前结束。 |
| `--isolation-max-drop` | 20% | 将最大吞吐下降不超过此值描述为“观测到业务吞吐影响较小”。这是本次实验的策略阈值，不是数据库通用合格标准。 |
| `--report-dir` | 自动生成新目录 | 可选覆盖输出位置，拒绝覆盖已有实验数据。 |

恢复阶段沿用 TPS 稳定规则，不再以 p95 为恢复通过条件；注入前基线仍需通过 TPS 与 p95 的既有稳定性门控。注入执行失败或故障不足一个窗口时，跳过自动恢复判定并报告证据不足。恢复判定额外等待一个窗口，容纳结果文件缓冲/迟到记录。结果源应及时刷新；超出该等待量的迟到数据可能影响估计。

## 持续服务和隔离结论的边界

正式故障阶段另有独立数据库探针，每个窗口尝试用当前账号新建连接并执行 `SELECT 1`。SQL 查询超时为 2 秒，单次观测等待最多 3 秒；探针失败可能由账号连接限额、连接拒绝或网络异常造成，不能直接解释为数据库进程崩溃。探针会额外产生连接和查询；驱动若不响应取消，底层连接尝试可能超出观测等待时间，不能保证硬终止。

- 完整故障窗口持续有业务事务成功：报告在该采样粒度内持续提供服务。
- 业务零吞吐，但每个完整窗口仍至少有一次探针成功：报告数据库可响应、业务可能受阻，区分业务受损和数据库进程宕机。
- 无成功业务，也无成功探针：报告证据不足，不自动判定数据库进程崩溃。
- 吞吐影响较小：只说明这次负载、故障及阈值下的观测结果，不证明数据库所有故障都具备隔离能力。存在业务错误时提示结合错误率判断。
- 注入失败、故障未开始、故障短于一个窗口、源文件丢失/截断/更换或数据不足：不作肯定的隔离与恢复结论。

分析假设基线无故障、业务负载持续且强度可比。业务压测主动停止、外部负载改变或结果日志缓冲也会影响 TPS，不能只凭曲线确定故障因果。撤销边界表示清理逻辑已返回，不独立保证所有残留表、锁及事务已清除。

## 数据保存位置

默认在 `result.csv` 同级生成 `dbchaos-reports/<时间戳-随机标识>/`。BenchmarkSQL 常将 result.csv 放在 `data/` 下，因此默认报告也在该 `data/` 目录下。控制台会输出本次绝对路径；Demo 自动沿用此规则。

- `throughput.csv`：基线、故障、恢复窗口的时间、成功数、错误数、成功 TPS、是否完整、结果时间戳是否覆盖窗口。末尾不足一个窗口的数据也保存，但不用于极值或恢复判定。
- `database-health.csv`：独立数据库探针的时间及 responsive/failed/timeout 结果。
- `resilience.json`：六项指标、下降与恢复比例、判据、证据是否完整和分析结论；不可获取的数值为 JSON null。
- `report.txt`：`reportTest()` 输出的业务韧性部分；原有异常详情继续在标准输出中，可随运行日志保存。

数据源优先读取同级 `runInfo.csv` 的 `sessionStart`，BenchmarkSQL 与 DBChaos 需使用相同时钟及时区。缺少 runInfo 时，按基线末次事件估计时间对齐，指标仅供参考；报告明确提示可能受日志缓冲影响，并将时间证据标记为不足，不确认恢复或隔离结论。多 run 混入、非法完整 CSV 记录及文件替换/截断会标记观测错误；未写完的半行等待下次读取，不重复计数。首次看到很久未更新的历史文件时，不会直接用其稳定历史放行注入。
