# 稳定门控、配置预检与结果分析使用指南

本文串联三项功能：等待业务稳定后注入、配置需求预检与失败报错、测试结果分析。命令均在 DBChaos 仓库根目录执行。各故障的专用参数见 [故障注入测试参数手册](故障注入测试参数手册.md)。

## 1. 构建与执行流程

需要 JDK、Maven，以及 `resources/db.properties` 中可用的 JDBC 连接配置。正常运行支持 Java 8+；仓库回归测试使用 `javac --release 8`，需要 JDK 9+。

```bash
bash build_for_linux.sh DBChaos-0.0.1
java -jar target/DBChaos-0.0.1.jar --help
java -jar target/DBChaos-0.0.1.jar txn uncommitted_txn --help
```

构建输出为 `target/DBChaos-0.0.1.jar`，脚本同时复制到仓库根目录。`--db` 可指定 `opengauss`、`postgresql`、`mysql` 或 `oceanbase`；省略时读取配置文件中的 `type`。连接覆盖参数为 `-url`、`-user`、`-password`；优先沿用已有配置，避免在命令记录中留下密码。

启用 `--wait-stable` 后，执行顺序为：

1. 读取外部业务结果，等待最近连续窗口的成功 TPS 与 P95 稳定，得到基线 P0。
2. 创建注入器与全程观测器，运行该故障已实现的参数和 SQL 预检。
3. 预检通过后记录 t0，准备故障对象并正式注入；期间持续采集业务和数据库响应。
4. 注入器及其清理逻辑返回后记录撤销时刻，继续观察业务恢复。
5. 输出执行报告、三项分析结论和原始数据。

稳定门控不会启动业务压测，预检也不是独立的 `--preflight` 命令。`--help` 不等待业务、不执行 SQL 预检或注入。未提供 `--wait-stable` 时直接进入故障执行流程，保留自动预检与基本执行报告，但没有全程业务韧性分析。

## 2. 一条命令完成等待、注入与分析

先单独启动 BenchmarkSQL，确认结果文件持续更新，并让业务持续运行到恢复观测结束。下面锁定已有业务表；按实际环境替换路径、表名和压力参数：

```bash
java -jar target/DBChaos-0.0.1.jar --db opengauss txn uncommitted_txn \
  -duration 30000 -table bmsql_stock -holders 1 -rows 10 \
  --wait-stable /path/to/benchmark/results \
  --baseline-window 10 --baseline-stable-windows 3 \
  --baseline-min-wait 30 --baseline-max-wait 180 \
  --baseline-json /path/to/benchmark/results/baseline.json \
  --recovery-timeout 180 --recovery-ratio 95 --isolation-max-drop 20
```

`-duration` 是故障参数，单位毫秒；门控和恢复等待时间使用秒，只有 `--baseline-poll` 使用毫秒。`--baseline-json` 可省略，表示额外保存基线文件，不控制全程报告的保存位置。故障持续时间应足够覆盖完整窗口；故障短于一个窗口时无法确认最低吞吐及恢复结论。

业务源支持直接传入 `result.csv`，或传入包含以下任一路径的目录：`result.csv`、`data/result.csv`、`benchmark_data/data/result.csv`、`run/result.csv`。应使用本次实验的结果，避免目录中混有多次运行。全程精确时间对齐依赖 `result.csv` 同级 `runInfo.csv` 的 `sessionStart`；缺少时仅估计对齐，不确认恢复或隔离结论。

### 稳定门控参数

下表参数使用双横线，可出现在故障命令的全局位置。`--baseline-*` 必须与 `--wait-stable` 一起使用，重复参数、未知后缀或缺值会报错。

| 参数 | 默认值 | 单位或要求 | 含义 |
| --- | --- | --- | --- |
| `--wait-stable <path>` | 不启用 | 结果目录或 CSV 文件 | 启用稳定门控及全程观测。 |
| `--baseline-window <n>` | 10 | 正整数秒 | 基线、故障、恢复的统计窗口长度。 |
| `--baseline-stable-windows <n>` | 3 | 正整数 | 连续稳定窗口数，也用于恢复判定。 |
| `--baseline-tps-cv <pct>` | 5 | 正数百分比 | 成功 TPS 变异系数上限，`5` 表示 5%。 |
| `--baseline-p95-swing <pct>` | 10 | 正数百分比 | 基线窗口 P95 波动上限。 |
| `--baseline-min-wait <n>` | 30 | 非负整数秒 | 从启动监控起至少等待多久。 |
| `--baseline-max-wait <n>` | 180 | 正整数秒 | 最长等待时间；未稳定则取消注入。 |
| `--baseline-poll <n>` | 1000 | 正整数毫秒 | 读取业务结果的轮询间隔。 |
| `--baseline-ignore-first <n>` | 0 | 非负整数秒 | 忽略业务结果时间轴起始部分。 |
| `--baseline-exclude-ttype <types>` | `DELIVERY_BG` | 逗号分隔 | 从业务统计中排除的事务类型。 |
| `--baseline-json <file>` | 不额外写文件 | 文件路径 | 保存稳定基线或超时诊断；写入失败也取消注入。 |

门控始终采用超时失败策略，不支持 `--baseline-on-timeout continue`。窗口数量不足、成功 TPS 为零或业务文件停止更新均不能作为稳定基线放行。

### 恢复与报告参数

这些参数也必须与 `--wait-stable` 同用。

| 参数 | 默认值 | 要求 | 含义 |
| --- | --- | --- | --- |
| `--recovery-timeout <sec>` | 180 | 正整数秒 | 撤销后最长恢复观测时间，确认恢复后可提前结束。 |
| `--recovery-ratio <pct>` | 95 | `(0,100]` | 每个恢复窗口成功 TPS 至少达到 P0 的此比例。 |
| `--isolation-max-drop <pct>` | 20 | `[0,100]` | 评价较好隔离效果所允许的最大吞吐下降。 |
| `--report-dir <path>` | 自动生成 | 新目录或空目录 | 覆盖报告输出目录，拒绝覆盖已有实验文件。 |

恢复还要求 TPS 连续稳定、每窗口成功响应 P95 不超过基线 1.2 倍加 1ms、错误率不超过基线加 1 个百分点。隔离评价的延迟阈值为基线 2 倍加 1ms。上述延迟与错误率阈值由 `ResilienceMonitor.Config` 定义，没有对应 CLI 参数。百分比参数传 `95`、`20`，不带 `%`。

### 只监控基线，不执行故障

```bash
java -jar target/DBChaos-0.0.1.jar monitor baseline \
  -result-dir /path/to/benchmark/results \
  -window 10 -stable-windows 3 -min-wait 30 -max-wait 180 \
  -json /path/to/benchmark/results/baseline.json -on-timeout fail
```

独立命令使用单横线 `-window`、`-poll` 等，其余名称和默认值与上表对应；另外支持 `-result` 作为 `-result-dir` 的别名。独立命令可指定 `-on-timeout continue`，超时返回 0 但不会执行故障，也不能把超时结果视为稳定基线。

## 3. 自动预检与失败排查

以下 8 个注入器已接入配置及能力预检（参数手册中的第 11～21 行含同一故障的多种模式）。其他用例不因此自动具备同等预检覆盖。

| 故障入口 | 主要检查 |
| --- | --- |
| `exec read_amp_trap` | 参数、默认隔离级别、事务超时、连接余量、双连接旧快照与扫描 SQL 能力。 |
| `txn uncommitted_txn` | 目标表、实际行数、事务超时、连接余量及 MySQL 表引擎。 |
| `txn duplicate_txn` | 模式、会话数、连接余量及 MySQL 所需数据库与默认引擎。 |
| `txn deadlock_storm` | 热点与锚点行数关系、目标表行数、连接余量、死锁检测及实际语句超时。 |
| `txn max_prepared` | Prepared 槽位或 XA 能力、实际准备与回滚、调整后的并发连接预算。 |
| `storage mvcc_bloat` | 旧快照保留、事务超时、连接余量及清理机制能力。 |
| `buffer memory_pressure` | 正数参数、数组上限、JVM 堆及并发缓冲预算、连接余量和 MySQL 包大小。 |
| `log massive_rollback` | 正数参数、有限且处于 0～1 的回滚概率、连接余量与事务引擎。 |

预检不需要 `DBCHAOS_PREFLIGHT_*` 环境配置。部分检查会创建小型临时测试对象、建立双连接或准备一个测试事务，并清理自己的对象；探测或清理失败均中止正式注入。不会自动修改全局数据库配置。

预检通过不表示磁盘/容器内存已验证充足，也不表示业务访问到了目标热点。详细检查边界和开发接口见 [预检与测试报告](预检环境检查接口.md)。

| 日志特征 | 含义与排查方向 |
| --- | --- |
| `[Gate] 性能未达到稳定条件` | 未进入故障执行。检查业务是否持续运行、窗口数量和稳定阈值；有基线 JSON 时查看其中的超时诊断。 |
| `[Gate] 监控参数错误` / `监控失败` | 未进入故障执行。检查路径、读写权限、文件格式与参数。 |
| `[Preflight] ... 预检失败，退出测试` | 正式注入未开始。按原始原因检查参数、连接、权限、隔离级别、目标表或所需数据库功能。 |
| `[TestReport] 执行状态=执行失败` | 异常传播到入口；报告保留失败阶段和异常样本，启用观测后也写入文件。 |
| `[TestReport] 执行结束，存在错误记录` | 注入线程或清理记录了异常。可能是预期故障现象，需要对照业务影响和注入计数。 |
| `未获取/未确认` 或 JSON `null` | 缺少证据或指标不适用。查看 `unavailable_reasons`，不要作为零值。 |

本流程常见退出码如下；退出码只表示执行状态，不是数据库韧性评分。旧入口仍可能只打印帮助或错误提示后返回，自动化时还应核对日志和报告。

| 退出码 | 含义 |
| --- | --- |
| `0` | 正常执行结束或显示帮助；不保证故障生效或性能恢复。 |
| `1` | 预检、故障执行、监控初始化等异常。 |
| `2` | 全局/门控参数解析或校验失败。故障内部参数预检失败通常为 `1`。 |
| `3` | 门控超时未稳定；部分既有注入器也用此码表示无有效注入，需结合日志区分。 |

保存控制台输出时，Bash 使用 `set -o pipefail`，避免 `tee` 掩盖 Java 的非零退出码：

```bash
set -o pipefail
java -jar target/DBChaos-0.0.1.jar txn uncommitted_txn \
  -duration 30000 -table bmsql_stock -holders 1 -rows 10 \
  --wait-stable /path/to/benchmark/results 2>&1 | tee experiment.log
```

## 4. 查看和分析测试结果

默认报告目录在实际 `result.csv` 同级的 `dbchaos-reports/<本次运行>/`，控制台输出绝对路径。如果结果文件位于 `data/`，报告也在该目录下。门控未通过时不会创建故障全程报告；按需使用 `--baseline-json` 并保留控制台日志。

| 文件 | 用途 |
| --- | --- |
| `report.txt` | 首先阅读三项核心结论：隔离效果、故障期间可用性、撤销后恢复；后面是依据、失败原因和原始执行明细。 |
| `summary.csv` | 结论与阶段指标表，适合汇总比较。 |
| `resilience.json` | 结构化指标、判断阈值、证据状态、失败阶段/样本/建议及指标缺失原因。 |
| `throughput.csv` | 逐窗口成功/错误数、成功 TPS、成功 P95、完整性和时间覆盖情况。 |
| `database-health.csv` | 独立 `SELECT 1` 探针证据；与真实业务可用性分开评价。 |

P0 是稳定基线成功 TPS，Pd 是故障完整窗口最低成功 TPS，Pr 是恢复窗口组平均成功 TPS；t0 是预检通过后的故障开始时间，td 是最低吞吐窗口结束时间，tr 是满足完整恢复条件的窗口组结束时间。最大下降为 `(P0-Pd)/P0`，恢复至基线比例为 `Pr/P0`，恢复用时从撤销时刻算到 tr。文本时间是 UTC，JSON 时间戳单位为毫秒。

分析时依次确认：是否真正开始故障、证据是否完整、业务吞吐/延迟/错误率受到何种影响、撤销后是否恢复。故障期间仍有成功事务但延迟明显变大，会报告“业务可用但响应变慢”；TPS 回升而 P95 或错误率未恢复，不会确认 tr。没有请求完成记录也不能直接认定数据库宕机。详见 [韧性指标与报告](韧性指标与报告.md)。

已有报告可重新生成可读摘要，不需要再次注入：

```bash
java -cp target/DBChaos-0.0.1.jar chaos.monitor.ResilienceReport /path/to/report
```

此命令读取 `resilience.json`，更新 `report.txt` 与 `summary.csv`，保留原始明细；重复执行不叠加摘要，不重算原始指标。旧 JSON 缺失的新字段仍显示“未获取/未确认”。

## 5. 实现位置与回归验证

| 职责 | 实现 |
| --- | --- |
| 参数分离、门控与退出处理 | `src/chaos/Main.java` |
| 基线读取及稳定判定 | `src/chaos/monitor/PerfBaselineMonitor.java` |
| 预检钩子、统一执行与失败汇总 | `src/chaos/core/BaseFaultInject.java` |
| SQL 条件与能力探测 | `src/chaos/core/PreflightChecks.java`、`PreflightProbes.java` 及各注入器 `preflight()` |
| 全程采集与结果落盘 | `src/chaos/monitor/ResilienceMonitor.java` |
| 指标与服务质量分析 | `src/chaos/monitor/ResilienceAnalysis.java`、`LatencyHistogram.java` |
| 可读摘要及 CSV 汇总 | `src/chaos/monitor/ResilienceReport.java` |

先构建 JAR，再运行本地回归：

```bash
bash build_for_linux.sh DBChaos-0.0.1
python3 -m unittest discover -s tests -p 'test_*.py' -v
```

本地回归使用模拟 JDBC 与合成业务文件，覆盖门控超时不注入、参数校验、SQL 预检、失败报告、吞吐/延迟/错误率分析、文件异常和报告再生成。真实数据库实验脚本在 `tests/opengauss_report/` 与 `tests/opengauss_resilience/`，会创建隔离数据库容器并执行压力测试，需单独准备环境；不能用本地回归通过替代真实故障效果验证。
