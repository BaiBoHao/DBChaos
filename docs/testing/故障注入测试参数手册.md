# DBChaos 故障注入测试参数手册

依据：`main` 分支提交 `d775b61` 的注册表、Java 注入器和脚本；整理日期：2026-10-17。

本文提供使用具名变量的测试命令模板，不代表这些参数已在当前数据库实测通过，也不保证达到资源上限或触发预期退化。本次仅检查源码和帮助入口，未执行数据库注入。

## 1. 使用前准备

DBChaos 是 JDBC 命令行工具，不要求在数据库服务器安装注入 agent。执行机需要能访问数据库端口，并具备 Java；从源码构建及使用连接探测脚本需要 JDK（含 `javac`），构建还需要 Maven。项目编译目标为 Java 8。

以下命令均从项目根目录运行，表内以 openGauss 为例；其他引擎需修改 `--db`、JDBC URL，并先核对对应行的兼容性备注。

```bash
cd /home/fenglin/ResBench/DBChaos
bash build_for_linux.sh
java -jar DBChaos-0.0.1.jar --help
```

先在 `resources/db.properties` 配置 `type` 及相应的 `url/user/password`，然后构建。`java -jar` 使用打包到 JAR 内的配置，修改源配置后应重新构建。也可以在每条注入命令中传入 `-url/-user/-password` 覆盖连接信息：

```bash
# 模板：先设置 JDBC_URL、DB_USER、DB_PASSWORD、STORM_CONCURRENCY、DURATION_MS。
# 变量未设置时会报错；参数就绪后执行会注入故障。
: "${JDBC_URL:?请设置 JDBC_URL}" "${DB_USER:?请设置 DB_USER}" "${DB_PASSWORD:?请设置 DB_PASSWORD}"
: "${STORM_CONCURRENCY:?请设置 STORM_CONCURRENCY}" "${DURATION_MS:?请设置 DURATION_MS}"
java -jar DBChaos-0.0.1.jar --db opengauss session max_connection \
  -url "${JDBC_URL}" \
  -user "${DB_USER}" -password "${DB_PASSWORD}" \
  -mode conn_storm -count "${STORM_CONCURRENCY}" -duration "${DURATION_MS}"
```

在真正注入前单独检查连接：

```bash
bash scripts/probe/check_db_connection.sh --db opengauss
bash scripts/probe/preflight_check.sh --db opengauss
```

表内命令默认复用已配置连接，不包含实际账号密码。常规连接、读写及在测试库内创建测试对象的权限按已具备处理，表中不再逐项重复；仅对可能需额外授权的参数修改等特殊操作注明。锁类测试需要现成业务表，其余多数场景自行建立测试对象。

仅在专用测试数据库运行：若干实现会先 `DROP TABLE IF EXISTS` 再建表；`plan_flip -table` 不能指向需要保留的业务表。多个相同场景也不宜同时运行，以免固定对象名称互相覆盖。

## 2. 故障、参数、命令及环境要求总表

统计口径：11 个实际故障注入器，对应注册表中 19 个故障预设；本表另外将读取放大的 3 个扫描选项分开展示，因此共 21 行。`quota test_case` 是占位验证入口，不计入故障。

“测试前提要求”列直接列出运行对应命令模板应满足的配置、数据与资源条件；命令行为及代码限制见其他列。配置值以目标数据库版本为准。

变量约定：命令使用 Bash 变量 `${变量名}`，运行前须在当前 shell 为该行所有变量赋值；可使用 `read -r DURATION_MS` 等方式交互输入。变量不提供固定默认值，应按目标环境和测试目标填写；没有赋值时不要执行命令。`-mode`、`-scan-mode` 的枚举值保留，用于区分场景；源码写死的递归深度、表数、配置常量等仍按实际值描述，不能通过这些变量调整。

## 3. 必须先确认的数据库条件

第 11～21 行对应的 8 个注入器已接入自动预检。`BaseFaultInject.preflight(String[] args)` 是可覆盖的预检钩子，默认空实现；这些注入器在正式建表、清表或启动压力线程前调用 `runPreflight`。预检异常会中止测试，CLI 输出 `[Preflight] ... 预检失败，退出测试` 并以状态码 1 退出；帮助命令不连接数据库或触发预检。

预检既核对配置和统计信息，也执行小规模实际能力探测：快照类创建唯一命名的单行测试表，在两个连接间验证旧快照、范围分组 SQL 和必要的表级清理选项；Prepared/XA 类实际准备一个唯一 GID，查询记录是否存在，再回滚。探测会清理自身对象，探测或清理失败均阻止正式注入；不会修改全局数据库配置，也不会操作其他测试的对象或 GID。

| 用例 | 手册前提要求与自动验证方式 |
| --- | --- |
| 11～13 | 检查正数参数、warmup < duration 和扫描模式；核对新连接默认事务隔离级别及事务存活超时，并以双连接更新/重复读取实测旧快照保留；执行全表计数和范围分组 SQL；核对连接余量、MySQL 默认事务引擎；不再强制检查服务器磁盘容量或要求提供增长预算，运行中的资源错误写入报告。 |
| 14 | 校验表名，每张表实际读取至少 holders × rows 行；核对事务存活超时、连接余量和 MySQL 目标表 InnoDB 引擎；业务是否访问被锁记录由业务指标判断，不再要求外部监控检查程序。 |
| 15～16 | 核对 UPDATE/INSERT 模式、正数参数、会话与监控连接余量，以及 MySQL 默认 InnoDB 引擎；MySQL 还检查源码需要的 dup_txn_inject 数据库已存在。 |
| 17 | 核对正数参数、waiters ≥ 2、hot-rows ≥ 4 且大于 anchors × anchor-rows、目标表实际行数、事务存活超时、连接余量；PG 类 deadlock_timeout 小于语句超时；新连接实际执行 SET 并回读语句超时；MySQL 死锁检测开启且目标表为 InnoDB。默认 hot-rows 为 64。 |
| 18 | 核对 duration/count/concurrency/factor、Prepared 配置和空闲槽位；实际执行与注入器相同的 PREPARE/XA 流程，查询记录保留并验证回滚命令成功；计算自适应并发后再次检查所需连接。MySQL 的 max_prepared_stmt_count 不作为 XA 容量依据；空 XA 没有保留记录时拒绝测试。 |
| 19 | 核对默认快照隔离级别、事务存活超时和连接余量，并实测双连接旧快照；PG 类核对 autovacuum/track_counts 且实际执行与源码相同的表级 autovacuum 选项；MySQL 核对 InnoDB 默认引擎和后台 purge 线程；运行中的磁盘和内存异常写入报告并给出检查建议。 |
| 20 | 核对正数参数、Java 数组上限、JVM 可用堆及并发缓冲预算、连接余量和 MySQL max_allowed_packet；不要求配置物理/容器内存或磁盘增长预算；运行中的资源异常写入报告。 |
| 21 | 核对正数参数、0～1 的有限回滚率、连接余量和 MySQL 默认 InnoDB 引擎；不要求提供磁盘目录或增长预算；运行中的资源异常写入报告。 |

必要的 SQL 条件或能力探测无法确认时退出。PG 类仅检查当前版本实际提供的事务/空闲事务超时项；连接余量是预检时的瞬时值。预检通过不保证运行中资源不再变化，也不代表预期扫描计划或业务退化已经发生。

所有故障复用现有数据库连接配置，不需要额外配置 `DBCHAOS_PREFLIGHT_CHECKER`、服务器目录或数据/日志增长预算。CLI 通过基类的 `executeWithReport` 统一调用抽象报告接口 `reportTest()`，输出执行状态、异常样本及相关环境检查建议；资源耗尽也可能是目标故障现象，报告不直接将其判定为环境问题或韧性不足。业务热点访问是否产生实际影响需结合业务指标确认。接口及报告说明见 [预检与测试报告](预检环境检查接口.md)。

下列 SQL 可用于人工复核，按目标引擎选择执行；DBChaos 不自动执行配置修改。

| 场景 | openGauss / PostgreSQL 检查示例 | 说明 |
| --- | --- | --- |
| 连接风暴/耗尽 | `SHOW max_connections;`、`SELECT count(*) FROM pg_stat_activity;` | 结合保留连接、角色限额和现有业务连接计算目标。测试时保留可用管理通道。 |
| openGauss 线程池 | `SHOW enable_thread_pool;`、`SHOW thread_pool_attr;` | 仅适用于提供这些参数的 openGauss 环境；PostgreSQL 没有这些通用参数。以实际版本输出为准。 |
| 自动统计与清理 | `SHOW autovacuum;`、`SHOW track_counts;` | 对提供这些参数的引擎核对后台统计/清理机制；不同 openGauss 存储引擎和版本可能不同。计划翻转另用 EXPLAIN 核实。 |
| 快照类 | `SHOW default_transaction_isolation;`、`SHOW transaction_isolation;` | 快照类注入器只关闭自动提交。需要核对注入账号新 JDBC 连接的默认隔离级别；事务级旧快照是否持续保留必须实测。 |
| Prepared 事务 | `SHOW max_prepared_transactions;`、`SELECT gid, prepared, owner, database FROM pg_prepared_xacts;` | 先确认容量和已有积压；执行前后比对实际记录。不要把“成功发送 PREPARE”当成实际积压数。 |
| 锁等待/死锁 | `SHOW deadlock_timeout;`、`SHOW statement_timeout;`、`SELECT * FROM pg_locks;` | 配置、权限和统计视图随引擎变化；语句过早超时可能先于死锁检测。 |
| 锁类目标表 | `SELECT count(*) FROM <TABLE_NAME>;` | 将 SQL 占位符 <TABLE_NAME> 替换为实际表名；记录数满足对应场景的行数关系，基准业务访问目标热点。 |

MySQL 环境另核对事务存储引擎（如 InnoDB）、连接限制、包大小、递归限制和锁等待超时；OceanBase 虽有 MySQL 语系分支，不代表所有 SQL/系统变量已逐项验证。CLI 中建议使用完整名称 `opengauss/postgresql/mysql/oceanbase`，避免别名在驱动初始化中的兼容性问题。

## 4. 如何判断测试是否有效

| 阶段 | 操作 | 至少记录的内容 |
| --- | --- | --- |
| 基线 | 先运行业务负载 1～3 分钟，不注入 | TPS/tpmC、P95/P99 延迟、错误率、连接数、CPU、磁盘吞吐 |
| 注入 | 一次只运行表内一个场景，按环境容量设置变量并逐级增加压力 | 注入成功数、SQL 错误类型、数据库指标是否达到目标条件、业务指标变化 |
| 恢复 | 注入结束后继续运行业务负载 1～3 分钟 | 是否恢复至基线、恢复用时、残留连接/锁/对象/Prepared 事务 |
| 结论 | 对比基线、注入、恢复三阶段 | 区分初始化失败、受控拒绝、真实资源压力、业务退化及恢复失败 |

建议记录命令输出，先设置 `SESSION_COUNT` 和 `DURATION_MS`，再在项目根目录执行：

```bash
mkdir -p docs/testing/logs
set -o pipefail
java -jar DBChaos-0.0.1.jar --db opengauss txn duplicate_txn \
  -sessions "${SESSION_COUNT}" -duration "${DURATION_MS}" -mode UPDATE \
  2>&1 | tee docs/testing/logs/duplicate_txn_update.log
```

通用报告会汇总注入器已记录的异常；正常退出不代表故障生效，不能只用 shell 返回码判断成功。部分 SQL 缺少统一超时，`-duration` 也不是对进程的严格截止时间。

正常路径下多数测试表会尝试自动删除，锁会回滚释放；异常退出不保证完整清理。递归/视图/Join 类尤其需要检查 `chaos_*` 对象。Prepared 清理应逐个确认属于本次测试的 GID，再执行 `ROLLBACK PREPARED '具体gid'`；MySQL 使用对应 `XA RECOVER` / `XA ROLLBACK` 流程，不能清理不明来源事务。
